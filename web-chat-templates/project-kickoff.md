# 项目启动对话模板

> 第一次和网页 AI 聊新项目时用这个模板。
> 位置：**Phase 1 的第一步**。先聊它，把需求和验收标准理清，再谈技术栈。
> 覆盖：想法、目标用户、核心功能、需求细化、**数据**、验收标准、边界。

---

## 开场白

```
我想做一个新项目，帮我理清思路。

项目名称（暂定）:
一句话描述:
目标用户:
核心场景（用户会怎么用）:
必须有的功能:
一定不做的功能:
我已有的技术能力:
部署方式（本地/网页/手机）:
```

如果这一版只是 MVP，开头就把它当**验证一个赌注**来聊，而不是当「小一点的完整版」：

```
这一版要验证的假设（我们在赌什么）:
什么结果说明值得继续:
什么结果说明该停:
大概多久能拿到这个结果:
```

多问这四句的理由：**MVP 的价值不在于做出来，在于回答「这个方向值不值得做」。** 答不出「什么结果说明该停」的话，做完了也不知道该不该继续。

## 需求细化

当 AI 给出初步方案后，追问具体需求：

```
帮我把这个功能拆成具体需求：
1. 用户会怎么操作
2. 每步操作的输入和输出是什么
3. 什么情况算成功
4. 什么情况算失败
5. 边界条件是什么
```

## 数据

功能理清后，把「数据」也理一遍。这一步现在做，比建库时再补便宜得多：

```
请根据上面的需求，列出这一版涉及的核心数据：

1. 有哪些实体？每个实体一句话说清它代表什么
2. 实体之间什么关系（一对一 / 一对多 / 多对多）
3. 每个实体归谁所有——谁能写，谁只能读
4. 哪些字段有格式约定？特别是：
   - 时间戳怎么存（带时区还是不带）
   - 金额怎么存（整数存最小单位，还是浮点）
   - 枚举值用字符串还是数字
5. 需要软删除吗？要审计字段吗（创建时间 / 更新时间 / 创建人）

只列这一版要做的，不要为想象中的未来设计。
```

## 验收标准

需求理清后，让 AI 写验收标准。**「什么算对」和「怎么跑」分开**——前者进 `## 验收标准`，
后者（跑哪些命令、什么算通过）进 `## Verification Plan`：

```
请帮我写出这个功能的验收标准：

行为类用：
- Given（在什么条件下）
- When（用户做什么操作）
- Then（应该发生什么）

给出至少 3 个正常场景和 2 个异常场景。

非行为类（性能、体积、限额）不用 Given/When/Then，直接写阈值，
例如「首屏加载 < 1.5s」「单文件 < 200KB」。

每条都要能被一条命令或一个可观察现象判定——「功能正常」不算。
```

## 追问模板

```
这个方案的主要风险是什么？
有没有更简单的替代方案？
MVP（最小可用版本）应该先做哪些功能？
哪些功能可以放到第二期？
如果只能做一件事，应该先做哪个？
```

## 结束前确认

```
请把我们讨论的结果整理成：
1. 项目一句话描述
2. 这一版要验证的假设 + 什么结果说明该停（没有就写「无」）
3. 核心功能列表（按优先级排序，不超过 5 个）
4. 明确不做的功能
5. 验收标准（行为类 Given/When/Then；非行为类写阈值）
6. 技术约束
7. 核心数据：实体、关系、归属（谁能写谁只能读）、字段格式约定
8. 术语表：讨论中出现的关键词，每个一句话定义，并指出容易混淆的近义词
9. 我们聊过但排除掉的方案，以及排除理由
10. 我明确要求反着常规来的地方，以及理由

第 7–10 项会被写进项目仓库长期维护，请写得能独立看懂，不要用「上面提到的那个」。

不要写代码。
```
