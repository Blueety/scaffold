# 前端设计对话模板

> 在网页 AI 中讨论界面设计时用这个模板。
> 位置：**技术栈定下来之后、压缩 Task Handoff 之前**。
> 覆盖：界面清单、视觉方向、组件库、交互与状态、响应式、可访问性、视觉验收标准。

## 为什么单独聊这一段

本地 Agent 拿到「现代、简洁、大气」会自己发挥，结果是它最熟悉的默认长相：居中的 hero、紫色渐变、圆角卡片网格、Inter 字体。这些不是你要的设计，是它的默认值。

这一步只干一件事：**把界面决策钉死成具体值**——hex、字号、间距、参考物、被排除的长相。没钉死的部分，本地 Agent 会替你做决定。

顺序：组件层依赖技术栈（SSR 还是 SPA、路由、样式方案），所以放在技术栈之后。纯视觉方向本来可以先聊，但分两轮不值得。

---

## 第一段：界面清单与布局骨架（先不谈颜色）

```
我要给 [项目一句话] 做前端。先只谈界面结构，不谈颜色和样式。

请列出：
1. 需要哪些页面 / 屏幕，每屏一句话职责
2. 页面之间怎么跳转（导航结构：侧栏 / 顶栏 / 无导航）
3. 每屏有哪些区域（侧栏 / 列表 / 详情 / 工具栏 / 空状态区……），各放什么
4. 主流程从进入到完成，用户依次看到哪几屏
5. 哪些是弹层 / 抽屉 / 模态，哪些是独立页面

用 ASCII 线框图画出每屏的区块布局，标出可滚动区、固定区、弹层。
每屏给一个短名字，以后代码里的组件名和路由名就用它。
```

## 第二段：视觉方向

```
现在谈视觉方向。不要只给形容词——「现代 / 简洁 / 大气 / 高级」没有信息量，
本地 Agent 会各自发挥。

请给出：
1. 3 个差异明显的方向，每个附 2–3 个具体参考（真实产品 / 站点 / 截图），
   说明参考它的哪一点：密度？留白？配色？字重？
2. 每个方向给具体值：背景色 / 主色 / 强调色 / 正文色 的 hex，
   字号阶梯（如 12/14/16/20/24），圆角、阴影、间距基准
3. 明暗模式：做不做，默认哪个
4. 密度：紧凑还是宽松，给出正文行高和控件高度
5. 字体：系统字体栈还是引入字体，中文回退是什么

最后给一句推荐，说明为什么适合 [目标用户 / 使用场景]。

这些是决定，不是建议。定下来就写死。
```

## 第三段：组件库与设计 token

```
结合已定的技术栈（[粘贴技术栈决定]），确定组件层。

1. 用现成组件库（shadcn/ui、Radix、MUI、Ant Design、Arco……）
   还是手写 + 样式方案（Tailwind / CSS Modules / vanilla-extract）？说明理由。
2. 设计 token 放哪、叫什么：颜色、间距、圆角、字号、阴影各一套。
3. 图标方案：图标库名 + 风格（线性 / 填充 / 双色）。
4. 哪些组件必须自定义（现成库的默认长相太「通用」、需要品牌感的）。
5. 明确要避开的默认长相（如 shadcn 默认味、Bootstrap 味、玻璃拟态、紫色渐变）。

区分：哪些是锁定的决定，哪些留给实现时再定。
```

## 第四段：交互与状态

```
逐个页面过一遍交互和状态。对每屏列出：

1. 加载中：骨架屏 / spinner / 保持旧数据？
2. 空状态：没数据时显示什么文案和什么操作？
3. 出错：请求失败显示什么，能不能重试？
4. 表单：字段、校验时机（失焦 / 提交）、错误文案放哪、提交中按钮什么状态？
5. 破坏性操作：删除 / 覆盖要不要二次确认，怎么确认？
6. 反馈：成功 / 失败怎么告诉用户（toast / 行内 / 页面级）？
7. 键盘：有没有快捷键，焦点顺序有没有要求？
8. 动效：哪里要过渡，多少毫秒，能不能关（prefers-reduced-motion）？

用「在 [页面]，[操作] 时，应该 [表现]」写，方便直接变成验收标准。
```

## 第五段：数据层

界面结构定完，接着定数据怎么流。**纯前端项目也要做这一段——它就是这个项目的架构。**

```
请帮我定前端的数据层：

1. 状态分几层？每层放哪：
   - 全局状态（用户信息、登录态、主题）→ 状态管理库
   - 页面状态（列表查询条件、分页）→ 页面组件
   - 组件状态（表单输入、弹窗开关）→ 组件内部
   - 服务端状态（服务器数据、缓存）→ 数据获取库（TanStack Query / SWR 等）
2. 到底需不需要状态管理库？先用这三个问题判断：
   - 有多少组件要共享这份数据？（2–3 个用 props / events 就够）
   - 这份数据经常变吗？（几乎不变的不必进全局）
   - 团队多大？
   从简单开始，按需升级——不要一上来就上 Redux。
3. 客户端 / 服务端的边界在哪？哪些逻辑在前端算，哪些必须回后端？
4. 怎么缓存、什么时候失效？（切页面重取？过期时间？手动失效？）
5. 要做乐观更新吗？失败怎么回滚？
6. 所有请求走统一封装吗？（超时、重试、错误格式、鉴权头）
```

**这一段最容易漏**：第四段管的是「每屏的四种状态」，不是「数据从哪来、放哪、什么时候失效」。纯前端项目没有这一段，就等于没有架构。

## 第六段：响应式与可访问性

```
1. 断点定在哪（如 640 / 768 / 1024 / 1280），各断点布局怎么变（折叠 / 隐藏 / 抽屉 / 单列）。
2. 最小支持宽度，窄到极限时哪个区域先让位。
3. 触屏还是桌面为主，要不要 hover 之外的操作方式。
4. 可访问性底线：键盘可达、对比度数值（如正文 ≥ 4.5:1）、图片 alt、
   语义标签、要不要照顾屏幕阅读器。
5. 国际化：要不要多语言 / RTL，文案里的变量怎么处理（如「已选 3 项」）。
6. 目标浏览器 / 设备清单。
```

## 第七段：视觉验收标准

```
把上面的决定变成可检查的清单，每条都要能用眼睛看或量出来，
不要「看起来协调」这种。

- [ ] 逐屏检查：元素齐全，布局和线框图一致
- [ ] 断点检查：每个断点截图，确认布局切换正确
- [ ] 状态检查：每屏的 加载 / 空 / 错误 / 有数据 四种状态都实现
- [ ] 对比度检查：正文、次要文字、按钮文字对背景的对比度达标
- [ ] 一致性检查：颜色 / 间距 / 圆角 / 字号全部来自 token，没有硬编码散值
```

## 收尾：压缩成 Task Handoff 的一段

```
请把前端设计的结论压缩成一段，格式对齐 Task Handoff 的「术语与决策」：

- 界面清单：每屏名字 + 一句话职责（这些名字以后就是组件名和路由名）
- 视觉 token：颜色 hex、字号阶梯、间距、圆角、阴影
- 组件库决定：用了什么、为什么、哪些自定义
- 已排除的方案：考虑过但没选的视觉方向 / 组件库，以及为什么不要
- 刻意偏离常规的地方：明确要求反着来的（如强制宽松行高、不做 hover 效果），以及理由
- 代码里看不见的约束：品牌色出处、必须嵌入的 logo / 素材路径、目标浏览器、已有设计稿链接

不要写代码。
```

> 收尾这段的输出分三处落：
> - **界面清单**（每屏名字 + 一句话职责）→ Task Handoff 的 `## Context Pointers`（它们是组件名和路由名的来源）
> - **视觉 token / 组件库决定 / 已排除的方案 / 刻意偏离常规 / 看不见的约束** → Task Handoff 的 `## 术语与决策` 的对应小类
> - **视觉验收标准** → Task Handoff 的 `## Done When`（每条要能判定，写法见 `docs/commands.md` 的「UI 变更怎么验」）
